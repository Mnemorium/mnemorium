# Issue Tracking

## Purpose

This page defines how issues are created, labelled, and triaged in this repository. It is the canonical reference for
the `triage` and `create-issue` agent skills.

## Tracker

Issues are tracked on GitHub Issues in the `Mnemorium/mnemorium` repository.

## Labels

GitHub creates a default label set in every repository (`bug`, `enhancement`, `documentation`, `question`, `wontfix`,
`duplicate`, `invalid`, `help wanted`, `good first issue`, `accessibility`). Those defaults are available without any
setup.

### State labels

The triage workflow uses four state labels, which must exist in the repository:

| Label             | Meaning                                       |
| ----------------- | --------------------------------------------- |
| `needs-triage`    | A maintainer still has to evaluate the issue. |
| `needs-info`      | Waiting on the reporter for more information. |
| `ready-for-agent` | Fully specified and ready for an AFK agent.   |
| `ready-for-human` | Requires a human to implement.                |

An issue that has not been triaged is unlabeled, which is equivalent to `needs-triage`.

### Labelling rules

- A triaged issue carries exactly one category label and exactly one state label.
- GitHub's default categories are used (`bug`, `enhancement`); no new category labels are required.
- Issues filed by CI default to `needs-triage` so that a maintainer reviews them.

## Creation paths

### Human

A maintainer creates and triages issues with the `triage` skill. Human-driven creation is outside the scope of
`create-issue`.

### CI (pre-existing violations)

The pull request review pipeline may detect violations that already exist in the repository and are not introduced by
the change under review. `review-pr` routes each such violation, grouped with related ones, to the `create-issue` skill,
which files one issue per group.

## Pre-existing decision request

Issues filed for pre-existing concerns are decision requests, not agent briefs: they describe a specific current code
state and ask engineering to decide what to do about it. A concern may not violate a documented rule at all; surfacing
it lets a maintainer decide whether to act and whether a rule is missing.

The title is `<rule> in <module>` when a rule applies, for example `Constraint naming in migrations`, or
`<dimension> concern in <module>` when none does.

The body is:

```markdown
> _This issue was generated by AI._

## Context

Found during the review of PR #<number> (<url>). The concern is pre-existing: it is not connected to that change.

## Evidence

- `<path>:<line>` — <fact>
  - Source: `<path>` § "<section>" | no rule covers this — potential rule gap

## Decision

Fix now, schedule the fix, waive the rule for this case, or add a rule that covers it?
```

Line references point at the code as it was when the issue was filed; the cited rule keeps the issue interpretable after
the code moves.

## Deduplication

Before filing, the review orchestrator lists the open issues and discards any pre-existing violation that already has an
equivalent issue. Discarded entries are also removed from the posted review comment, so the comment only shows newly
tracked debt.

## Disclosure

Every issue and comment generated by an automated agent opens with an AI-generated disclaimer:

```markdown
> _This issue was generated by AI._
```

## CI requirements

The review workflow must be able to reach GitHub:

- grant `pull-requests: write` to read the pull request diff and post the review comment, and `issues: write` to file
  issues;
- run the action with `use_github_token: true` so that the GitHub CLI has an authenticated token;
- ensure the `gh` command is available on the runner.

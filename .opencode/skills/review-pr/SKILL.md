# Review PR

Define the review process and the exact report contract for a pull request review.

## When to use

- The review orchestrator reviews a pull request in CI.
- A maintainer asks for a pull request review.

## Inputs

- The pull request number, read from the GitHub Action context (its `<pull_request>` block carries `Number`,
  `URL`, `Base Branch`, and `Head Branch`).
- The unified diff, obtained with the `github-pr-diff` tool. It contains `diff --git`, `---`/`+++` file paths,
  and `@@` hunk headers. This is the only artifact under review.

The CI invocation always requests a full review of all dimensions.

## Process

1. Read the pull request number from the context and call `github-pr-diff`. If the tool fails, or the diff is
   empty or not a unified diff, skip to **Not performed**.
2. Dispatch the hidden `reviewer` subagent with the Task tool (`subagent_type: "reviewer"`). Embed in the task:
   - the diff verbatim;
   - the **Review output contract** below, verbatim.
3. The reviewer returns two parts: the review body to publish, and a separate pre-existing-concerns list. Call
   `github-issue_search` to list the open issues and drop every concern that already has an equivalent open
   issue. Group the remaining concerns by relatedness (your judgment). If at least one group remains, load the
   `create-issue` skill and file one issue per group.
4. Append a `Pre-existing` section built from the filed issues to the end of the review body. Emit the combined
   text as your final message; the opencode GitHub Action publishes it as the pull request comment. Do not
   rewrite the review body, and do not add any other section.

You never edit the repository, and you never run shell commands to publish.

## Review output contract

Embed this section verbatim in the `reviewer` task. The reviewer returns two clearly delimited parts.

### Part 1 — review body

The review body is the text to publish. It starts with the disclosure and contains the verdict, the checklist,
and the findings.

#### Disclosure

The first line is:

```markdown
> *This review was generated by AI.*
```

#### Verdict

```markdown
## Verdict

<emoji> **<pass | pass_with_notes | fail>** — X blocker(s), Y violation(s), Z suggestion(s)
```

- `❌ fail` — at least one `Introduced` Blocker or Violation.
- `⚠️ pass_with_notes` — no Blocker or Violation, but at least one `Introduced` Suggestion.
- `✅ pass` — no findings introduced by the diff.

#### Checklist

Always list all eight dimensions, in this order, using the evaluation of the lines the diff adds or changes:

```markdown
## Checklist

- [x] Correctness & safety
- [ ] StyleGuide compliance — 2 violations
- [x] Architecture & boundaries
- [x] REST & OpenAPI
- [x] Persistence & SQL
- [x] Tests
- [x] Security
- [x] Documentation & hygiene
```

A row is `[ ]` (no-pass) if and only if that dimension has at least one `Introduced` Blocker or Violation; annotate
it with the count and kind. Otherwise it is `[x]`. A dimension the diff does not touch is still evaluated and passes.
`Introduced` Suggestions do not flip a row. Pre-existing concerns never affect a row.

#### Findings

Group `Introduced` findings by severity, strongest first. Omit an empty group.

```markdown
## Findings

### Blocker

- **`path:line`** — <fact>
  - Source: `docs/development/StyleGuide.md` § "<section>"

### Violation

- ...

### Suggestion

- ...
```

Every entry carries the diff location, one factual sentence, and the authoritative source. No `Introduced` entry
without a source. Do not use preference language.

### Part 2 — pre-existing concerns

A separate list, not part of the published body. A concern is something noticed while reading the repository that
is not connected to the change but appears to breach one of the eight dimensions. It may or may not violate a
documented rule; the point is to let a developer decide whether to act or whether a rule is missing.

```markdown
- `path:line` — dimension: <dimension>
  - Fact: <what the code does and why it looks wrong>
  - Source: <`path` § "<section>" | no rule covers this — potential rule gap>
  - Suggested issue: <one-line title>
```

Use a `Source` when a rule applies; otherwise state the potential rule gap explicitly.

### Not performed

When the diff is absent, empty, or malformed, emit only this body (no Verdict, no Checklist):

```markdown
> *This review was generated by AI.*

## Review not performed

Reason: <no diff provided | diff is empty | diff is not a unified diff>

No verdict was produced.
```

## Published comment

The orchestrator appends the `Pre-existing` section, built from the issues it filed, to the end of the review
body. Concerns already tracked by an open issue are dropped from both the section and the filing.

```markdown
## Pre-existing (not introduced by this change)

- **`path:line`** — <fact>
  - Source: <`path` § "<section>" | no rule covers this — potential rule gap>
  - Issue: <url>
```

The issue template and label vocabulary live in `docs/development/IssueTracking.md`.

## Constraints

- Human-readable markdown only; no machine-readable block.
- The reviewer returns the review body and the pre-existing list separately; the published body is the review
  body with the `Pre-existing` section appended, and nothing else.
- `Introduced` findings require a rulebook source; pre-existing concerns may state a potential rule gap.
- One finding per distinct issue; cite the rulebook section, never paraphrase it.
